# 主体数据冲突处理闭环实现记录

日期：2026-08-20  
环境：`10.210.0.62` Docker DEV  
数据库版本：V25

## 1. 处理结论

Atlas 已将“企业主档与工商变更中的主体关键字段不一致”从一个普通提示，升级为正式的
人工异常处理节点。系统不再一边提示冲突、一边继续显示“计算风险”或允许生成报告。

当前 V1 对法定代表人冲突采取以下策略：

1. Agent 自动识别主体、采集数据和检索公开信息；
2. 先比较主档与工商变更的数据时点：主档 `data_as_of` 晚于变更记录时，该变更按历史轨迹
   处理，不再把历史任职人误判为当前冲突；
3. 只有变更数据不早于主档，且法定代表人仍不一致时，任务才进入
   `WAITING_SUBJECT_DATA_REVIEW`；
4. 页面下一步明确显示“核对主体数据”，并同时展示主档值、最新变更值、变更日期和来源记录；
5. 报告生成门禁增加 `SUBJECT_DATA_CONFLICT`，在冲突未处理前禁止评分闭环和正式报告生成；
6. 运营人员只有在完成外部核对并填写依据后，才能选择“以当前主档为准并继续”；
7. 选择结果绑定当前冻结数据快照。后续重新采集形成新快照时，旧选择不会被静默复用；
8. 决定人、决定时间、数据快照、处理说明和选择结果进入审计日志。

如果运营人员不能确认当前主档正确，V1 不提供“凭感觉选最新变更”的按钮，应先修正 ES
或上游工商数据，再重启任务。这样可以避免把一个界面选择变成新的错误主档。

## 2. 状态与门禁

新增任务状态：

- `WAITING_SUBJECT_DATA_REVIEW`：等待核对主体关键字段；
- `REVIEW_SUBJECT_DATA`：工作台和 Agent 对话中的下一步动作。

主要状态流转为：

```text
CALCULATING_RISK
  -> 检测到未处理的主体冲突
WAITING_SUBJECT_DATA_REVIEW
  -> 重新执行时发现当前主档已晚于历史变更：自动清除假冲突
  -> 或运营人员填写核对依据并确认仍然存在的当前冲突
CALCULATING_RISK
  -> Agent 自动续跑评分、确认和报告
COMPLETED
```

运行监控已把新状态归类为“待人工”，不会再误计为执行中或停滞任务。

## 3. 数据与接口

Flyway V25 新增 `subject_data_conflict_resolution`，按“任务 + 数据快照”唯一保存处理结果。
当前支持的决定为 `ACCEPT_MASTER`，保留后续接入权威数据源覆盖或主档修复流程的扩展空间。

新增接口：

```http
POST /api/tasks/{taskId}/subject-data-conflict-resolution
X-Operator-Id: <operator>
Content-Type: application/json

{
  "decision": "ACCEPT_MASTER",
  "note": "已核对权威公示信息，确认当前企业主档为准"
}
```

任务工作台响应新增：

- `subject_data_conflicts`：当前快照检测到的冲突；
- `subject_data_conflict_resolution`：当前快照已保存的处理决定；
- `next_action=REVIEW_SUBJECT_DATA`：明确的人工入口；
- `readiness_blockers` 中的 `SUBJECT_DATA_CONFLICT`：报告生成硬门禁。

## 4. 页面交互

任务工作台中的主体冲突区现在具备真实操作能力：

- 未处理时显示冲突双方、日期和来源；
- 要求运营人员填写核对依据；
- 提供“确认以当前主档为准并继续”；
- 完成后显示处理人、处理时间和说明；
- 待处理页、任务列表和 Agent 对话均能识别新状态及新动作。

这是一个受控异常入口，不是新增一个需要日常逐步点击的固定流程。没有主体冲突的任务仍由
Agent 连续自动执行。
