# Atlas 验收标准与任务进度重新评估

评估日期：2026-08-05  
评估范围：`tasks/atlas-agent/` 当前代码、设计与实施记录、自动化测试，以及 `10.210.0.62` DEV 环境实际状态。  
面向对象：产品负责人、研发负责人、运营验收人员。

## 一、执行结论

Atlas 当前应定义为：**已部署的集成工程原型 / 内部验证环境**，尚不能定义为“业务试用版完成”，更不能定义为“生产候选版完成”。

此前进度记录的主要偏差，是把以下三类结论混在了一起：

1. 页面、接口和数据表已经存在；
2. 自动化测试通过；
3. 运营人员能够用真实资料完成业务任务，并得到与原流程一致、可解释、可复核的正式报告。

当前第 1 类已大量完成，第 2 类工程测试通过，但第 3 类尚未形成闭环。2026-08-05 复核得到：

- 后端 37 个测试类、96 项测试全部通过；前端生产构建成功，9 项页面/连线测试全部通过。
- DEV 环境保留 8 条任务，但完成任务为 0，已生成报告为 0；其中 7 条是长期停留在非终态的测试任务，不能解释为“正在执行”。
- 抽查任务已取得 ES 企业快照并形成 25 条候选证据，但确认 0、驳回 0、正文采集 0、风险评分未形成、报告未生成。
- ES 和 Tavily 的实际运行能力为 READY，但主要依赖环境变量或代码默认值；数据源、搜索、模型、规则和 5 个 Skill 的管理版本均仍是草稿，未形成生效绑定。
- 联网模型未配置，运行时为 `DETERMINISTIC_RULES / RULE_FALLBACK`，不能验收模型研判能力。
- 规则页展示了 11 个基础权重和后来确认的事件最低分，但没有完整呈现原 `RiskScoreService`、`RiskEnum`、`updateRiskInfo` 中的行业、地区、标签优先级、工商倍数、关系融合和标签生成逻辑。
- Skill 管理具备版本、启停、依赖和审计底座，但大部分“参数、输入输出契约、失败策略”尚未真正控制执行器；现阶段不能把“可填写”认定为“可配置”。
- 黄金样本基础设施已建成，但验收清单为 0，缺少 20～50 组历史旧报告与人工终稿，正式盲测尚未开始。

因此，后续不能再以“代码模块数、页面数、接口数、测试数”作为项目完成度的主要口径。项目主线必须回到：**真实旧报告能否由运营人员在页面内完成更新，并生成可信、可解释、可下载的正式 DOCX**。

## 二、重新定义验收标准

### 2.1 五级验收状态

| 等级 | 名称 | 判定条件 | 能否称为完成 |
|---|---|---|---|
| E0 | 未开始 | 没有可运行实现或只有设计 | 否 |
| E1 | 已实现 | 代码、页面或数据结构存在 | 否 |
| E2 | 技术验证通过 | 自动化测试证明接口、状态、持久化和关键算法按测试用例工作 | 只能称“技术完成” |
| E3 | 集成环境验证通过 | 在部署环境使用真实依赖完成运行，配置、审计和失败路径均有证据 | 只能称“集成完成” |
| E4 | 业务验收通过 | 运营人员使用真实历史资料，从页面完成全流程；结果达到业务指标并签字确认 | 可以称“V1 业务完成” |
| E5 | 生产验收通过 | 身份权限、安全、容量、备份恢复、回滚和故障演练通过 | 可以称“生产就绪” |

任何任务的最终状态取它通过的最低完整层级。只有页面或接口存在时，不再记录为“已完成”；自动化测试通过时，明确写为“E2 技术验证通过”。

### 2.2 六道验收门

| 验收门 | 核心问题 | 必须保存的证据 |
|---|---|---|
| G0 需求可追溯 | 用户提出的每项规则和流程，是否能定位到实现与测试 | 需求—代码—配置—测试—页面对应矩阵 |
| G1 实现完整性 | 实际执行逻辑是否覆盖需求，而不是只做展示或元数据 | 代码路径、配置消费点、规则清单 |
| G2 技术正确性 | 测试是否验证业务语义，而非只检查接口返回或页面包含文字 | 单元/集成/E2E 测试报告与关键断言 |
| G3 运行时有效性 | 发布配置是否真的改变新任务行为，失败是否按约定停止 | 生效版本、任务快照、执行轨迹、失败记录 |
| G4 真实业务闭环 | 运营人员是否能用真实旧报告完成更新并得到可用 DOCX | 真实输入、人工决策、评分对比、输出报告、验收记录 |
| G5 生产可运营性 | 系统是否能安全、稳定、可恢复地长期运行 | 权限、安全、容量、备份恢复、回滚和故障演练记录 |

### 2.3 V1 必过业务验收项

以下标准建议作为“单企业旧风险报告更新”V1 的正式 Definition of Done：

1. **真实页面闭环**：至少 1 份正式旧 DOCX 必须先通过 W19 冒烟门；最终用 20～50 组历史旧报告与人工终稿完成盲测。不得绕过页面直接写库或调用内部接口拼出结果。
2. **主体识别**：验收样本主体识别正确率 100%；无法唯一识别时停止并要求处理，不允许猜测。
3. **数据失败策略**：ES、公开搜索或必需模型调用失败时，任务 100% 停止并明确提示；不得把失败解释为“无风险”。
4. **评分迁移完整性**：对具备完整旧模型特征的样本，新旧原始分差异为 0（浮点计算允许预先约定不超过 0.01 的舍入误差）；39 个风险标签、地区规则、标签优先级、行业分、工商倍数、关系融合和事件最低分必须逐项可追溯。沿用物化旧分的样本必须明确标记，不能冒充“新引擎重算一致”。
5. **人工分语义**：原始分、规则分、事件保底分、人工调整分和最终分分别保存；人工调整必须记录原因、证据、操作者和时间，不能覆盖原始分。
6. **舆情证据**：全称、简称、品牌、门店等身份词均可检索；纳入报告的每条证据必须可回溯到来源、命中身份词、标题/摘要或正文和人工确认结果。建议在黄金样本上以人工终稿为基准统计准确率、召回率和无关证据率，再冻结目标值。
7. **关键事件最低分**：已确认且具备证据的失联、欠薪、门店关闭分别执行最低 6、6、8 分；测试必须同时覆盖命中、不命中、证据不足、多个事件叠加和人工改分。
8. **报告质量**：输出 DOCX 可正常打开，保留 V1 正式模板结构；关键字段完整、无未替换占位符、无错位或破损表格，引用与评分可从报告回到任务证据。
9. **配置真实性**：只有被运行代码读取并能通过回放证明影响结果的字段，才允许出现在“可配置”页面。展示性字段必须标注“说明信息”或暂时移除。
10. **运营可恢复**：任务状态准确，不把长期停滞任务统计为活跃；可重试步骤须幂等，不可重试失败须明确结束；所有人工操作与配置变更可审计。
11. **缺陷门禁**：正式验收样本中 P0/P1 缺陷为 0；低等级缺陷有明确处置结论。主观感受可作为易用性评价，但不能替代上述可复核标准。

### 4.2 关键缺口说明

#### W19：真实闭环是当前最早阻塞门

没有“一份真实旧报告从页面走完”的证据，后续所有“规则管理完成、模板管理完成、监控完成”都缺少统一业务载体。W19 必须先于继续扩展管理页面。

#### W20/W22：旧评分模型不是 11 个权重加 3 个最低分

当前可见配置覆盖了部分基础权重和业务后来确认的事件最低分，但原资产还包括 39 个 `RiskEnum` 标签、不同地区方案的优先级、行业分、资本/年限/上市/变更倍数、关系风险融合、溢出压缩以及 `updateRiskInfo` 的组织和标签生成逻辑。未形成逐项对应矩阵前，不能声称“旧评分模型完整迁移”。

#### W24：配置存在不等于配置有效

Skill 的启停和依赖门可以影响任务，版本与快照可审计；但参数、输入输出契约和失败策略多数没有执行器消费点。规则页也存在类似问题：若字段只被保存和展示，不参与运行或验证，它就是说明性元数据，不是能力配置。

#### W25：监控需要反映真实运行语义

当前把所有非终态任务计为活跃，导致停滞两天的任务仍显示“活跃”。正式验收应引入心跳/最近进展时间、停滞阈值和明确终止状态，避免运营人员误判。

## 六、建议的后续顺序

### P1：先补 W19，一份真实报告走通

- 保存输入、每一步状态、配置快照、人工决策和最终文件，作为第一份可追溯样本。

### P2：建立旧模型逐项追溯矩阵

- 将 `RiskScoreService`、39 个 `RiskEnum`、`updateRiskInfo` 与新引擎、规则配置、UI 和测试逐项对照。
- 每个规则标明“已迁移 / 沿用物化分 / 缺失 / 待业务确认”。
- 先让页面准确展示真实执行逻辑，再讨论哪些规则允许运营配置。

### P3：消除伪配置

- Skill、规则、连接器和模板字段必须具备“保存—校验—发布—新任务快照—执行轨迹—回放差异”证据。

- 在 DEV 发布一组可回滚版本，用两条任务证明配置变化确实影响运行。

### P4：执行 20～50 份黄金样本盲测

- 导入历史旧报告与人工终稿，冻结样本清单。
- 由运营人员独立操作，逐份记录主体、证据、评分、DOCX 和缺陷结果。
- 达到 P0/P1 缺陷为 0、评分与标签等价、报告结构完整后，才宣布 E4。

### P5：完成 W27

- 接入生产 ES 和统一身份，完成权限、密钥、TLS、容量与超时策略。
- 实施数据库、配置、模板和报告文件的备份恢复与回滚演练。
- 完成故障注入、重试幂等和恢复时间验证后，才宣布 E5。

## 七、需要用户提供或确认的最小事项

当前可继续推进 P0～P3，不需要等待真实生产 ES。进入 P4 前，需要：

1. 20～50 组“历史旧报告 + 人工最终版”；可先提供 5 组做试运行，再扩到正式样本集。
2. 对旧代码中疑似反常但必须兼容的规则，确认是“原样保留”还是“作为新版规则修正”。
3. 指定 1～2 名实际运营人员参与盲测，并对报告可用性签字确认。
