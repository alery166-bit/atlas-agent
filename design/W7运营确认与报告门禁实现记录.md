# W7 运营确认与报告门禁实现记录

## 1. 目标

把原先测试或人工直接修改任务状态的做法，替换为正式的运营确认流程。

运营确认不是简单地把任务从 `CALCULATING_RISK` 改成
`WAITING_OPERATOR_CONFIRMATION`，而是对“当前可出报告的输入状态”生成一份可追溯确认快照。

V1 仍不设置普通运营、高级运营和审核人角色。一次有效的运营确认，即可使任务满足报告生成条件。

## 2. 确认范围

每份确认记录绑定以下内容：

- 最新企业数据快照；
- 最新风险评分快照，包括原始分、人工分和风险等级；
- 评分人工调整记录；
- 当前全部公开证据的确认或驳回状态；
- 已抓取网页正文的最新成功快照及内容哈希；
- 确认人、确认说明和确认时间。

系统将上述内容规范化后计算 `review_state_hash`。报告生成时会重新计算当前状态，
只有最新确认记录与当前状态完全匹配，才允许生成报告。

## 3. 业务规则

1. 任务处于 `CALCULATING_RISK` 或 `WAITING_OPERATOR_CONFIRMATION` 时可以确认。
2. 必须已经形成企业数据快照和风险评分快照。
3. 风险评分必须来自最新企业数据快照。
4. 所有公开证据必须明确标记为 `CONFIRMED` 或 `REJECTED`，不能残留
   `UNVERIFIED`。
5. 同一任务、同一状态的重复确认幂等复用，不新增重复记录。
6. 首次有效确认将任务推进到 `WAITING_OPERATOR_CONFIRMATION`。
7. 确认后修改人工分、证据结论或证据正文，原确认立即失效。
8. 原确认失效后，报告接口返回 `REPORT_GENERATION_INVALID`，要求重新确认。
9. 每个新生成的报告版本保存 `operator_confirmation_id`，形成报告到确认记录的审计链。
10. V7 之前已存在的历史报告允许 `operator_confirmation_id` 为空，避免丢弃既有资产。

## 4. 接口

### 4.1 完成运营确认

```http
POST /api/tasks/{taskId}/operator-confirmation
X-Operator-Id: operator-001
Content-Type: application/json

{
  "note": "已核对工商信息、评分和全部舆情证据"
}
```

成功后返回确认记录。若存在未处理证据，返回：

```json
{
  "code": "OPERATOR_CONFIRMATION_INVALID"
}
```

### 4.2 查询确认历史

```http
GET /api/tasks/{taskId}/operator-confirmations
```

按确认时间倒序返回。

### 4.3 生成报告

```http
POST /api/tasks/{taskId}/reports
X-Operator-Id: operator-001
```

报告生成前校验最新确认是否仍与当前输入匹配。生成后的报告响应包含
`operator_confirmation_id`。

## 5. 数据结构

新增表 `operator_confirmation`：

| 字段 | 说明 |
|---|---|
| `confirmation_id` | 确认记录 ID |
| `task_id` | 任务 ID |
| `data_snapshot_id` | 企业数据快照 ID |
| `score_snapshot_id` | 风险评分快照 ID |
| `review_state_hash` | 确认状态哈希 |
| `confirmed_evidence_count` | 已确认公开证据数 |
| `rejected_evidence_count` | 已驳回公开证据数 |
| `operator_id` | 操作人 |
| `note` | 确认说明 |
| `confirmed_at` | 确认时间 |

`task_id + review_state_hash` 设置唯一约束，用于数据库层防止重复确认。

`report_version` 新增可空字段 `operator_confirmation_id`，新报告必须写入，
历史报告保持兼容。

## 6. 验证覆盖

自动化测试覆盖：

- 未处理公开证据时确认失败；
- 全部证据确认或驳回后确认成功；
- 同一状态重复确认保持幂等；
- 人工调整风险分后，原确认失效；
- 确认失效时禁止生成报告；
- 重新确认后报告生成成功；
- 报告版本正确保存确认记录 ID；
- Flyway V7 可在 H2 测试库完整执行；
- OpenAPI 文档包含确认与确认历史接口。

## 7. 后续 UI 对接

运营工作台应在“生成报告”前展示一个确认卡片，至少包含：

- 企业数据快照时间；
- 原始分和人工分；
- 已确认、已驳回、未处理证据数量；
- 未处理项快捷入口；
- 确认说明输入框；
- “确认并进入报告生成”按钮。

当评分或证据在确认后发生变化，卡片应显示“确认已失效”，并禁用报告生成按钮，
直到运营人员重新确认。
