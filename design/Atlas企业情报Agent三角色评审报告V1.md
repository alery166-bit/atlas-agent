# Atlas 企业情报 Agent 三角色评审报告 V1.0

> 评审对象：`Atlas企业情报Agent详细设计V1.md`、`atlas-agent-full-platform.html`  
> 评审角色：产品、研发、运营  
> 评审日期：2026-07-29  
> 评审结论：**方向通过，附条件进入研发；不建议按当前14页面平台范围一次性开工。**

---

## 1. 执行结论

详细设计的方向是正确的，尤其是以下判断比较成熟：

- 一个企业情报 Agent + 多个 Skills；
- 自然语言是统一任务入口；
- Agent负责编排，事实和评分由确定性服务提供；
- 企业主体未确认前不查询下游业务数据；
- 证据、风险事件、模型判断和人工调整分别保存；
- 不迁移全部ES mapping；
- 通过兼容层保留现有风险模型；
- 以“更新一份企业风险报告”作为第一条生产链路。

但设计文档的完整度已经接近“平台蓝图”，原型也一次性展现了14个页面。这容易让项目从“解决运营人员更新风险报告的问题”扩张为“建设完整Agent平台”。

综合判断：

| 评审项 | 评分 | 结论 |
|---|---:|---|
| 详细设计方向 | 8.2/10 | 架构清楚，关键边界正确 |
| 产品范围控制 | 6.5/10 | 文档提出控制范围，但页面和模块仍偏大 |
| 技术可实施性 | 7.2/10 | 可落地，但几个核心技术决策尚未冻结 |
| 运营适用性 | 6.8/10 | 主流程正确，人工复核工作台仍不够具体 |
| 原型完整度 | 7.0/10 | 信息架构完整，关键深层交互不足 |
| 生产就绪度 | 5.5/10 | 还不能直接按当前设计全面开发 |

建议状态为：

> **有条件通过立项评审。允许先启动统一数据契约、主体识别、风险快照和评分兼容层；在关键P0问题关闭前，不启动完整平台的全面建设。**

## 2. 产品角色评审

### 2.1 产品视角结论

产品方向成立，但目前仍然存在“解决一个明确业务问题”和“建设一个通用企业情报平台”之间的摇摆。

详细设计第27章明确建议从“输入企业和旧报告，更新工商、风险和舆情并生成新报告”开始，这是正确的产品切口。问题在于原型同时展示了Agent对话、调查任务、企业档案、报告中心、Skills、工具、策略、数据源、规则、模板、模型、评测、监控、审计和权限，视觉上仍然像一个已经完整产品化的平台。

### 2.2 产品设计做得好的地方

#### 1. 统一对话入口正确

不设置“风险排查/招商线索”两个模式按钮，符合用户的真实工作方式。运营人员表达目标，Agent识别意图并组合能力，比让用户理解系统内部模块更自然。

#### 2. 一个Agent的定位清楚

详细设计没有把多个Skill包装成多个虚假的Agent角色，避免了产品概念膨胀。

#### 3. 证据优先形成可信差异

企查查类产品擅长返回数据，Atlas的产品差异应当是：

- 理解运营任务；
- 对比旧报告；
- 发现新增变化；
- 核验证据；
- 解释风险分；
- 输出可人工复核的报告。

详细设计已经围绕这一差异组织，而不是只做企业数据问答。

#### 4. 人工复核不是补丁

文档把主体确认、证据核验、风险改分和报告发布设计成正式流程，而不是系统失败后的兜底，这符合专业企业风险产品要求。

#### 5. 第一条生产场景选择合理

“更新旧风险报告”同时覆盖主体、工商、风险、舆情、评分、报告和人工复核，验证价值比单纯做企业问答更充分。

### 2.3 产品P0问题

#### P0-1：第一版价值主张仍需冻结

当前设计同时服务：

- 企业基础查询；
- 风险调查；
- 风险报告更新；
- 负面舆情；
- 招商线索；
- 关联风险；
- 报告生成；
- 企业比较。

这些最终都可以存在，但第一版只能有一个主价值：

> **帮助企业风险运营人员更快、更可靠地更新企业风险报告。**

建议招商线索保留在总体架构中，但不进入第一条正式验收链路。否则产品、数据、评测和运营规则都会同时分叉。

#### P0-2：缺少真正的“人工复核产品”

文档对人工复核写得较完整，但原型没有独立的复核中心或高保真复核页面。

目前对话页只展示：

- 风险摘要；
- 简短证据；
- “展开调查/暂不展开”；
- 生成报告。

这不足以验证运营人员怎样完成：

- 主体归属确认；
- 事件合并；
- 证据驳回；
- 风险类型调整；
- 严重程度调整；
- 风险分修改；
- 修改原因；
- 二次审核；
- 报告段落回写。

如果复核体验不成立，整个Agent最终仍会退化为“生成一份需要人工重做的草稿”。

#### P0-3：产品成功指标还偏技术

现有验收指标包括主体准确率、工具成功率、证据覆盖率和风险准确率，这些必要但不够。

第一版必须增加业务指标：

| 指标 | 建议定义 |
|---|---|
| 单份报告平均处理时间 | 从任务创建到提交审核 |
| 人工有效操作时间 | 排除等待搜索和模型的时间 |
| 报告一次通过率 | 无需退回重做的报告比例 |
| 人工修改率 | Agent结论被修改的比例 |
| 重大结论驳回率 | 高风险结论被人工驳回的比例 |
| 新增风险发现率 | 相比旧流程新增发现的有效风险 |
| 运营人员周活跃率 | 实际使用产品的目标用户比例 |
| 对话任务完成率 | 发起后完成到报告草稿的比例 |

#### P0-4：招商线索缺少具体业务上下文

招商价值取决于：

- 服务哪个地区；
- 目标产业；
- 招商政策；
- 可提供的园区、资金、场地和服务；
- 哪类企业被认为值得跟进。

当前原型可以展示“招商价值”，但在这些条件未配置时，结论只能是泛化分析。第一版若保留招商能力，应定位为“经营活跃信号汇总”，而不是完整招商推荐。

### 2.4 产品P1问题

1. 缺少旧报告上传、识别和确认入口；
2. 缺少批量企业任务入口；
3. 缺少任务交接、评论、@审核人和催办；
4. 缺少报告新旧版本差异页面；
5. 缺少用户首次使用引导和示例提示词；
6. 缺少“快速查询”和“正式调查”的成本/时间差异；
7. 五套视觉主题适合当前评审，不建议生产长期保留全部主题；
8. 普通运营人员不应看到Skills、工具、模型、数据源等全部平台配置页面。

### 2.5 产品角色结论

产品评审结论：**有条件通过。**

通过条件：

- 冻结第一版主价值；
- 补齐高保真人工复核流程；
- 增加业务效率指标；
- 把平台管理员功能从运营主导航中分离。

## 3. 研发角色评审

### 3.1 研发视角结论

详细设计的分层是合理的：

```text
Agent → Skill → Tool → Domain Service → Adapter → Data Source
```

这比让模型直接查询CSV或ES安全得多。统一企业、证据、风险事件、风险分快照和报告版本的设计，也为后续数据源迁移留出了空间。

但文档当前更接近“逻辑架构”，尚未达到可以直接拆研发任务的完整物理设计。几个未决定的问题会直接影响数据库、索引、接口、缓存和迁移方案。

### 3.2 研发设计做得好的地方

#### 1. Agent与业务服务边界正确

文档明确禁止：

- 模型自行计算风险分；
- 模型直接读原始ES；
- 模型把自由推断写成事实；
- 主体未确认就查询下游；
- 报告模型重新搜索和修改分数。

这是系统可控性的基础。

#### 2. 统一业务契约优于复制旧mapping

现有数据字段存在snake_case、camelCase、旧拼写和批次差异。通过适配器转成统一业务模型，比继续把旧ES结构扩散到新系统更可维护。

#### 3. 对旧评分代码的处理方向正确

文档没有要求立即重写 `RiskScoreService`，而是提出：

- 建立黄金回归样本；
- 构建 `RiskScoreFacade`；
- 隔离数据读取；
- 隔离保存副作用；
- 新旧结果并行对照；
- 逐条迁移规则。

这显著降低了模型迁移风险。

#### 4. 任务状态机和断点续跑必要

企业调查包含外部搜索、长文抽取、人工确认和报告生成，不适合一个同步HTTP请求完成。状态机、幂等键和快照ID设计是正确的。

#### 5. 证据模型基本合理

证据包含来源、原始ID、URL、发生/公示/抓取时间、主体匹配、核验状态和查询溯源，可以支持审计和报告引用。

### 3.3 研发P0问题

#### P0-1：稳定企业ID尚未决定

文档指出不能继续只使用“企业名称MD5”，但Atlas稳定 `company_id` 如何生成尚未决定。

这是所有表、API、缓存、任务和报告的根主键，必须在正式建库前冻结。

建议：

- Atlas生成不可变内部UUID；
- 统一社会信用代码作为强身份锚点，但不是唯一主键；
- 保留旧名称MD5为 `legacy_company_id`；
- 用 `company_identity_binding` 保存各数据源ID；
- 企业更名只更新名称，不更换Atlas ID；
- 合并、注销、历史主体关系单独表达。

#### P0-2：旧风险模型仍不是可直接迁移的纯计算引擎

当前 `updateRiskInfo` 涉及：

- 企业名MD5；
- Redis和异步任务；
- 多索引读取；
- 风险标签写入；
- 动态预警；
- 评分保存；
- 人工干预状态。

仅增加Facade还不够，需要明确两阶段方案：

1. 兼容阶段：在隔离运行环境中调用旧服务，并把副作用限制在测试/影子索引；
2. 纯化阶段：把输入快照构建、评分计算和结果保存拆成三个组件。

否则在线Agent调用评分时可能意外触发现有预警、ES写入和队列任务。

#### P0-3：缺少物理数据设计

统一模型已经定义字段，但还缺：

- PostgreSQL表结构和索引；
- ES逻辑视图的物理索引方案；
- 证据正文放数据库还是对象存储；
- 大字段和摘要的分离；
- `risk_event` 去重键；
- 分区策略；
- 数据保留期限；
- 历史版本膨胀控制；
- 预计企业数、风险事件数和每日增量；
- 查询性能基准。

没有这些，研发无法准确评估资源和工期。

#### P0-4：数据同步与一致性方案不完整

文档定义了CSV/ES适配器和离线降级，但尚未明确：

- CSV如何首次导入；
- ES如何增量同步；
- 水位字段是什么；
- 删除、移出、撤销如何同步；
- 同一事件多来源冲突如何更新；
- 快照一致性；
- 报告生成过程中数据更新如何处理；
- 离线快照和在线数据冲突时以谁为准。

建议报告任务在主体确认后生成 `data_snapshot_id`，后续评分和报告均基于同一快照，避免调查过程中事实漂移。

#### P0-5：非功能指标未冻结

监控项已有，但研发仍需要明确SLO：

| 场景 | 建议目标 |
|---|---:|
| 企业主体精确查询P95 | ≤2秒 |
| 企业画像P95 | ≤5秒 |
| 结构化风险调查P95 | ≤15秒 |
| 含外部舆情的调查 | 异步，首个进度≤3秒 |
| 标准报告草稿 | ≤3分钟 |
| 服务月可用性 | ≥99.5% |
| 单任务最大重试 | 3次 |
| 同时进行的深度调查 | 根据环境压测冻结 |
| 单任务模型费用上限 | 产品和运维共同确定 |

#### P0-6：公开检索接入风险没有落实

“搜索主流搜索引擎”不是一个可直接开发的接口，需要决定：

- 使用官方API、第三方聚合还是浏览器自动化；
- 调用频率和配额；
- robots、版权和内容保存边界；
- 登录、验证码和反爬；
- 搜索结果摘要是否允许长期存储；
- 原文失效后的证据策略。

该问题会直接决定失联、欠薪、闭店能力是否可用。

### 3.4 研发P1问题

1. Tool通用错误结构还需要错误码、是否可重试、降级来源和分页游标；
2. 人工确认需要乐观锁和并发冲突处理；
3. 任务取消后外部Worker如何停止尚未定义；
4. Prompt注入防护仍停留在原则，需要正文与指令隔离、外部内容不可信标记和工具白名单；
5. 报告模板字段契约和Word渲染服务未具体定义；
6. 批量任务与交互任务需要独立队列和配额；
7. 模型网关需明确数据出境和敏感字段策略；
8. 缺少前端页面与后端API的逐页对应表；
9. 原型是单HTML静态实现，只能验证信息架构，不能直接演进为生产前端；
10. 五套主题会增加生产CSS维护和视觉回归成本，应在开发前选定一套。

### 3.5 研发角色结论

研发评审结论：**架构通过，详细设计尚需补一版技术设计。**

允许先开发：

- 统一数据契约；
- CSV抽样适配器；
- 主体解析原型服务；
- 风险快照Builder；
- 现有评分黄金回归。

暂不建议全面开发：

- 完整14页面平台；
- 正式舆情采集；
- 评分写入生产；
- 完整报告发布；
- 招商推荐。

## 4. 运营角色评审

### 4.1 运营视角结论

系统已经抓住当前人工工作的主要步骤：

```text
下载旧报告
→ 核对工商
→ 搜索负面信息
→ 人工研判
→ 调分
→ 修改报告
```

对话入口、调查进度、企业档案、风险摘要、证据引用和报告中心都符合运营人员认知。但“运营真正花时间的地方”不是查看摘要，而是处理不确定信息和修改报告，目前原型在这两个环节还不够深。

### 4.2 运营设计做得好的地方

#### 1. 不要求运营理解Agent内部结构

运营人员直接输入任务，不需要先配置Skill或选择技术流程。

#### 2. 能看到执行进度和数据源状态

原型展示了主体识别、工商查询、内部ES、公开舆情和证据核验进度，有助于理解系统为什么还没完成。

#### 3. 区分“已确认”和“待核实”

失联、拖欠工资和门店关闭使用不同状态，避免把所有搜索结果写成确定风险。

#### 4. 支持只看旧报告后的新增风险

这比每次重新阅读全部企业信息更符合实际工作。

#### 5. 报告和历史调查归入企业档案

运营后续回看时可以理解“上次为什么这样判断”，而不是只拿到一个最终Word文件。

### 4.3 运营P0问题

#### P0-1：缺少完整的待办和复核队列

运营每天面对的是一批任务，不只是一段对话。

需要独立页面支持：

- 待确认主体；
- 待核验舆情；
- 待调整标签；
- 待审核改分；
- 待补充报告字段；
- 待发布报告；
- 超时任务；
- 被退回任务。

并支持按风险类型、企业、任务人、等待时长和优先级筛选。

#### P0-2：证据查看深度不足

原型中的“证据[1-3]”只是文本摘要。运营需要同时看到：

- 原始网页或文书；
- 标题、来源、时间；
- 命中的企业名称和关键词；
- 主体匹配依据；
- 同一事件的多来源；
- 是否重复；
- 是否已失效；
- 关联的是目标主体、品牌、门店还是关联公司；
- 一键确认、驳回和调整。

#### P0-3：缺少报告差异工作台

更新报告最重要的不是生成一份新报告，而是回答：

- 哪些工商信息变了；
- 哪些风险新增了；
- 哪些旧风险解除或仍有效；
- 风险分为什么变了；
- 哪些文字由Agent修改；
- 哪些内容沿用旧报告；
- 哪些字段还缺失。

需要一个“旧版—新版—证据”差异页面，而不是只提供报告列表和预览。

#### P0-4：人工改分流程需要更具体

运营修改风险分时需要：

- 显示模型原始分；
- 显示命中规则；
- 选择调整原因；
- 填写说明；
- 绑定证据；
- 展示调整后影响；
- 高风险改分提交审核；
- 保留上次人工调整；
- 明确本次是否继续沿用。

当前设计原则正确，但原型未呈现。

#### P0-5：数据新鲜度必须在结论旁显示

不能只在企业页顶部显示一个总体更新时间。运营需要知道：

- 工商截至哪天；
- 司法截至哪天；
- 投诉截至哪天；
- 舆情查询发生在什么时候；
- 哪个数据源使用了离线快照；
- 哪个查询失败。

否则正式报告中的“未发现”无法判断可靠性。

### 4.4 运营P1问题

1. 需要批量导入企业和旧报告；
2. 需要任务分派、转交和协作评论；
3. 需要相似历史案例和常用修改话术；
4. 需要报告发布前检查清单；
5. 需要一键复制证据摘要到报告；
6. 需要批量确认低风险、无变化企业；
7. 需要导出本周新增风险和待处理清单；
8. 需要区分系统等待时间和人工处理时间；
9. 普通运营导航应减少为5～6个页面；
10. Skills、工具、数据源、模型和权限应只对管理员展示。

### 4.5 运营角色结论

运营评审结论：**业务流程方向通过，原型暂不能完成运营验收。**

下一轮运营评审应重点演示：

1. 上传旧报告；
2. 主体确认；
3. 查看新增风险；
4. 证据核验；
5. 调整风险标签和分数；
6. 比较报告版本；
7. 提交审核；
8. 导出正式报告。

## 6. 三个角色共同确认的P0事项

### P0-1 冻结第一版范围

招商线索进入下一阶段，不与第一版同时验收。

### P0-2 确定稳定企业ID

正式建库前完成内部ID、信用代码、旧MD5和外部来源ID的绑定方案。

### P0-3 增加高保真人工复核原型

至少包含：

- 主体确认；
- 舆情证据核验；
- 事件合并；
- 标签调整；
- 人工改分；
- 报告差异；
- 审核发布。

### P0-4 完成旧评分模型隔离方案

### P0-5 确认公开舆情接入方式

明确数据源、授权、配额、存储、失效和合规策略。

### P0-6 补充物理数据与同步设计

形成数据库表、索引、容量、增量、快照和冲突处理方案。

### P0-7 建立真实验收集

从现有历史人工结果和报告中形成固定样本，先测出现有人工流程基线，再验收Agent是否提升。

## 9. 最终评审意见

### 产品负责人意见

> 产品方向成立，但必须把第一版重新收缩到“更新企业风险报告”这一条价值链。补齐人工复核和业务指标后通过。

### 研发负责人意见

> 分层架构和资产复用策略合理，可以启动数据契约、主体识别和评分回归工作。稳定企业ID、物理数据设计、评分副作用隔离和舆情接入方式确定前，不应全面开工。

### 运营负责人意见

> 系统理解了现有人工流程，但运营最重要的证据核验、人工改分和报告差异还没有在原型中真正展开。下一轮应按一份真实报告完整演示，不再主要展示配置页面。

### 联合决议

> **有条件通过。建议进入“核心生产链路设计与实现”阶段，但不进入“完整平台全面研发”阶段。**
