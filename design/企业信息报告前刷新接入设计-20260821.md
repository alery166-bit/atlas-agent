# 企业信息报告前刷新接入设计

日期：2026-08-21  
状态：Atlas 内置直连接入已完成；真实接口联调与 ES 投影后置

## 1. 结论

Atlas 应在每次新的企业风险研判中，先取得最新企业结构化信息，再冻结数据快照、检索公开信息、
研判证据、评分并生成报告。更新动作应插入“主体确认”之后、“数据快照”之前；如果任务在人工处理
阶段停留过久，生成正式报告前还要再次检查数据时效，过期则自动刷新并重跑受影响的下游步骤。

不建议直接调用现有 `/test/updateCompany`，也不建议把旧 `ElasticStorageServiceImpl` 原样迁入
Atlas。推荐复用 `harvest` 的接口采集规则、DTO 字段映射和 `process` 中有价值的标准化逻辑，重新
封装为有明确结果状态的企业数据刷新连接器，然后写入 Atlas 的统一数据结构。

V1 页面仍保持四段任务进度。“企业数据更新”作为“主体与数据”内部步骤展示，不新增独立 Agent，
也暂不新增第六个可见 Skill；把 `skill.company.snapshot` 升级为 V2，语义调整为“更新企业数据并
冻结快照”。

## 2. 旧代码实际链路

实际源码目录为：

`D:\IdeaProjects\dispatcher_service\src\main\java\com\rong360\dispatcher\xlb`

当前入口和调用链如下：

```text
/test/updateCompany?name=...&type=...&apiType=...
  -> DataSyncService.syncData
     -> ApiCollectorAdapter.collect
        -> 4713 接口按企业名称/信用代码取得 eid
        -> 按 ApiInfoType 顺序调用 31 类企业接口
     -> DataProcess.process
        -> 商标申请人英文名补齐
        -> 专利去重、申请人补齐、状态和类型格式化
     -> IDataStorageService.save
        -> type 为空：MySQL 与旧 ES 双写
        -> type=es：只写旧 ES
  -> updateAddressFour
  -> updateRiskInfo
  -> updateCompanyCbdLabel
```

31 类采集范围分为：

| 分组 | 类型 | 数量 | Atlas V1 用途 |
|---|---|---:|---|
| 主体与报告基础信息 | BASE、CONTACT、SHAREHOLDER、INVESTMENT、BRANCH、CHANGE、MAIN_PERSON | 7 | 报告必需；MAIN_PERSON 同时补核心人员 |
| 结构化风险事件 | DISHONEST、EXECUTOR、LIMIT、JUDGEMENT、EQUITY_FREEZE、EQUITY_PLEDGE、EQUITY_HOSTAGE、FILLING、ABNORMAL、ILLEGAL、ADMINISTRATIVE、ENVIRONMENT、CANCELLATION、LIQUIDATION、TAX_ILLEGAL、AUCTION、BANKRUPTCY | 17 | 报告和评分必需 |
| 企业资产 | TAX_CREDIT、FINANCING、BUSINESS、CERTIFICATE、TRADEMARK、PATENT、COPYRIGHT | 7 | 风险报告非必需，供企业画像和后续招商使用 |

现有接口并不包含 Atlas 当前资产模型中的标准、荣誉等全部类别；`LONG_TEXT`/新闻采集也被关闭，
因此不能把这 31 类描述为“所有企业数据”。舆情和投诉仍应继续走 Atlas 的公开信息检索链路。

## 3. 不能直接复用旧入口的原因

### 3.1 失败和空数据没有被区分

- 多数单项采集方法捕获异常后只写日志，把字段保留为空集合。
- `collect` 最外层也捕获异常，但没有返回逐项成功、失败、超时和记录数。
- `companyBase` 在真实接口成功前就创建并挂载空 DTO；`DataSyncService` 只判断该 DTO 非空，存在
  把失败结果当成功保存的可能。
- 旧 ES 存储普遍采用“先按企业删除、再逐条写入”，上游请求失败产生空集合时，可能把原有数据
  误删成空。

Atlas 已明确“必需数据源失败就停止，不能输出无风险”，所以必须把以下状态严格分开：

- `SUCCESS_WITH_DATA`：成功且有数据；
- `SUCCESS_EMPTY`：接口明确成功但没有记录，可以清除该类别的旧当前数据；
- `FAILED`：接口失败，不能删除旧数据，报告必需类别失败时任务停止；
- `SKIPPED`：本次策略明确不采集。

### 3.2 数据结构不兼容

旧存储写入 `sentiment_company_*` 等大量历史索引，并以规范化企业名称的 MD5 作为企业 ID；Atlas
使用 `atlas-company-*` 五类统一索引、`atlas_company_id` 路由、稳定来源记录 ID 和统一来源元数据。
直接调用旧入口后，Atlas 当前 ES Adapter 看不到新增数据。

### 3.3 有不应带入 Atlas 的副作用

旧入口采集完成后会调用旧系统的地址处理、`updateRiskInfo` 和 CBD 标签逻辑。Atlas 已有版本化、
确定性的风险评分和审计链，不能让刷新接口在任务之外修改风险分，也不需要 CBD 标签。

### 3.4 接口与安全不满足服务调用要求

- 入口位于 `TestController`，成功返回空字符串、失败返回企业名，无法可靠判断结果。
- 没有刷新任务 ID、幂等键、逐类别状态、数据校验摘要和审计信息。
- 外部数据服务凭据写在源码常量中。接入前必须迁到受控密钥配置并轮换现有凭据，不得复制进
  Atlas、前端、日志或镜像。
- 31 类分页接口串行执行，当前调用可能较慢，不适合长期占用前端请求。

## 4. 目标工作流

```text
运营人员输入企业名称/信用代码
  -> 创建研判任务并冻结配置、Skill 版本
  -> 主体解析
     -> ES 有唯一主体：绑定主体
     -> ES 无主体：调用更新数据源解析候选，必要时只让人确认主体
  -> 更新企业数据（新增内部步骤）
     -> 建立 refresh_job，按企业加分布式锁
     -> 调用企业信息更新连接器
     -> 采集 24 个报告必需类别
     -> 校验企业名称、信用代码、来源 eid 和逐类别结果
     -> 生成 Atlas 统一结构并写入 ES
     -> 写入后读取校验、保存刷新清单和数据摘要
  -> 冻结本任务 DataSnapshot
  -> 搜索舆情与投诉
  -> LLM 证据研判；不确定项转人工
  -> 确定性规则评分
  -> 报告时效与版本门禁
  -> 生成 DOCX
```

报告必需类别全部成功后才能冻结快照。企业资产 7 类可以在同一刷新作业中采集，但其失败暂不阻断
V1 风险报告；需要在刷新结果中显示“资产数据更新不完整”，后续招商报告启用时再把对应类别改为
必需。

## 5. 推荐组件设计

### 5.1 Atlas 侧端口

新增 `CompanyRefreshPort`，避免工作流依赖小蓝本或 dispatcher 的具体实现：

```text
startRefresh(taskId, resolvedCompany, requestedCategories, idempotencyKey)
getRefreshJob(refreshJobId)
```

返回结果至少包含：

- 刷新任务 ID、调用方任务 ID、数据提供方和连接器版本；
- 目标企业 eid、企业全称、统一信用代码；
- 开始、完成和源数据时间；
- 每个类别的状态、记录数、耗时、校验摘要和脱敏错误码；
- 总体状态 `RUNNING/SUCCEEDED/PARTIAL/FAILED`；
- 规范化后的企业数据载荷或 Atlas ES 写入批次 ID。

### 5.2 更新连接器

本轮根据明确边界“不改动 dispatcher”，已把有价值的采集规则迁入 Atlas 的
`atlas-adapter-company-refresh` 模块，dispatcher 全程只读。迁入内容包括：

- `ApiCollectorAdapter` 中的 API ID、分页和字段解析；
- `CompanyInfoDto` 及 DTO；
- `DataProcess` 中的专利、商标标准化。

不复用：

- `TestController`；
- `DataSyncService` 当前无结果值的编排；
- MySQL/旧 ES 双写实现；
- 旧风险评分、地址四级和 CBD 标签副作用。

本轮没有复制 dispatcher 的旧存储、旧评分、测试 Controller 或源码凭据。连接参数只从 Atlas
服务器环境变量读取。当前 V1 由工作流同步调用，并在每类接口前后续租；调用量扩大后再演进为
持久化异步作业：

```text
POST /internal/v1/company-refresh-jobs
GET  /internal/v1/company-refresh-jobs/{jobId}
```

Atlas 可沿用现有模型研判作业的“启动、进度、失败恢复、只重试失败项”模式。

Atlas 当前不依赖 dispatcher 工程及其旧 Elasticsearch 客户端。

### 5.3 Atlas 数据发布

更新结果应映射到现有统一索引，而不是创建 31 个索引：

| 更新数据 | Atlas 目标 |
|---|---|
| 企业主档 | `atlas-company-read` |
| 变更及 17 类风险事项 | `atlas-company-event-read` |
| 股东、人员、投资、分支 | `atlas-company-relation-read` |
| 电话、邮箱、官网、地址 | `atlas-company-contact-read` |
| 证书、商标、专利、软著、融资、产品、纳税信用 | `atlas-company-asset-read` |

文档必须包含 `refresh_job_id`、来源系统、来源 eid、来源记录 ID、采集时间、源数据时间和内容哈希。
稳定文档 ID 使用来源系统、来源类别、来源记录 ID的哈希，不能用 `HashMap` 无序遍历拼接。

发布原则：

1. 单类别采集成功后才能替换该类别；
2. `FAILED` 不删除旧数据；
3. `SUCCESS_EMPTY` 才允许把该类别当前记录置空；
4. 全部报告必需类别发布完成并读回校验后，才把刷新作业标记成功；
5. Atlas 再从成功批次冻结数据快照，确保报告输入可追溯。

生产强化阶段建议使用“每企业当前批次指针”或 staging + commit 机制，避免五个索引之间出现半批
新、半批旧的数据组合。

## 6. Atlas 状态与存储调整

建议数据库增加：

- `company_refresh_job`：刷新作业总体状态、企业、任务、版本、幂等键、时间、错误；
- `company_refresh_category_result`：31 类逐项状态、数量、耗时、摘要；
- `data_snapshot.refresh_job_id`：快照绑定本次刷新；
- `data_snapshot.source_fetched_at`：报告的数据时点。

任务状态增加：

- `REFRESHING_COMPANY_DATA`；
- `WAITING_COMPANY_REFRESH`（若采用异步作业，可只作为运行态）；
- 错误码 `COMPANY_REFRESH_UNAVAILABLE`、`COMPANY_REFRESH_REQUIRED_CATEGORY_FAILED`、
  `COMPANY_REFRESH_SUBJECT_MISMATCH`、`COMPANY_REFRESH_PUBLISH_FAILED`。

刷新失败属于可重试来源失败。重试必须复用相同幂等键，只补采失败类别；同一家企业同时创建多个
任务时合并为同一个进行中的刷新作业，避免重复调用和重复费用。

## 7. 时效与“更新报告”语义

建议内部试用默认口径：

- 每个新研判任务必须发起一次企业信息刷新；
- 同企业并发任务共享同一刷新作业；
- 正式报告生成时，刷新数据超过 24 小时则自动重新刷新；
- 若刷新后内容哈希未变化，可以复用已完成的证据决定和评分输入；
- 若主档、关系或风险事件发生变化，则创建新快照，旧评分和旧确认失效，自动重跑受影响步骤；
- 刷新失败时停止，不使用旧数据冒充最新数据，也不输出“无风险”。

对话语义需要明确区分：

- “更新风险报告”：创建关联的新研判版本，先刷新企业数据，再重新研判和生成报告；
- “重新生成/修复版式”：仅在数据、证据、评分、确认都仍有效时重渲染同一快照。

现有“更新报告”只基于历史冻结快照重新渲染的逻辑需要调整，否则不符合本次确定的新口径。

## 8. 页面调整

不增加一级页面或额外人工按钮：

- 工作台第一阶段仍叫“主体与数据”，子状态显示“正在更新企业信息”“已更新 24/24 个报告数据
  类别”“7 个资产类别部分失败”等；
- 任务详情展示数据提供方、最新更新时间、刷新作业 ID、各类别数量和失败项；
- 数据源管理增加“企业信息更新接口”，展示是否可用、最近成功时间、平均耗时和失败率；
- 刷新失败进入任务错误状态，由系统自动重试，耗尽后才给运营人员“重试更新”；
- DOCX 首页或数据说明增加“企业结构化数据更新至 YYYY-MM-DD HH:mm”。

## 9. 实施顺序

### 阶段 A：安全接口与契约

1. 把旧接口凭据迁出源码并轮换；
2. 为 31 类采集增加结构化状态，严格区分成功空结果和失败；
3. 新增正式内部刷新接口、幂等键、鉴权和逐类别结果；
4. 对 3 家企业验证主档、关系、风险事件和空数据语义。

### 阶段 B：Atlas 工作流接入

1. 新增刷新端口、作业表、状态和错误码；
2. 在主体绑定后、快照前启动刷新；
3. 把结果转换到 Atlas 五类索引并完成读回校验；
4. 将 `skill.company.snapshot` 发布 V2，并让新任务冻结 V2；
5. 保持旧任务继续使用创建时冻结的 V1。

### 阶段 C：报告时效门禁

1. 新任务强制绑定成功刷新作业；
2. 报告生成前检查 24 小时时效；
3. 数据变化自动使旧评分、确认和报告失效；
4. 把“更新报告”调整为完整的新研判版本。

### 阶段 D：内部试用验证

1. 从 30 家候选中先选 10 家执行；
2. 验证接口失败、成功空数据、主体改名、风险新增、并发重复任务和服务重启；
3. 对比刷新前后 ES、快照、分数和 DOCX；
4. 通过后扩大到 30～50 家内部试用。

## 10. 实施前需要确认的外部条件

编码前可以先按以下推荐默认值推进，真正联调前仍需确认：

- Atlas 服务器是否能访问 dispatcher 内部接口或小蓝本接口；
- 使用 dispatcher 作为短期连接器，还是允许 Atlas 直接接小蓝本；
- 小蓝本接口调用额度、并发和限速；
- 报告数据有效期采用推荐的 24 小时，还是更短；
- 7 类资产更新失败是否继续允许生成风险报告（推荐允许，但必须提示并留痕）。

## 11. 2026-08-21 实施结果

已完成：

- 新增独立 Maven 模块 `atlas-adapter-company-refresh`，dispatcher 未发生任何改动；
- 迁入 31 类接口 ID、分页/游标规则和 Atlas 统一字段映射，其中 24 类为风险报告必需，7 类资产为
  可选；
- 严格区分“成功有数据、成功空数据、失败”，任一报告必需类别失败即停止任务，不把失败解释成
  无风险；
- 用信用代码优先、企业全称兜底进行主体一致性校验，主体错配停止；
- 新数据直接形成本次任务的不可变 `DataSnapshot`，工商主档、关系、变更、17 类风险事件和 7 类
  资产上下文参与内容哈希；
- 每类调用前后刷新任务租约，并把 31 类状态、记录数、刷新 ID、提供方和采集时间写入任务事件；
- 对话中的“更新报告”不再基于旧快照直接重渲染，而是创建新任务，从企业信息刷新开始重新执行；
- Docker 与 Spring 配置已增加刷新开关、地址、凭据引用、超时、重试、分页和记录数上限，源码和
  镜像不保存凭据；
- 适配器 3 项自动化测试通过，覆盖正常映射、必需类别失败和可选类别失败；报告更新定向集成测试
  2 项通过。

当前采用“刷新结果直接冻结到 PostgreSQL 任务快照”的安全路径，尚不覆盖写 Atlas 共享 ES。这样
已经保证新报告读取本次最新接口结果，同时不会因某次接口失败删除 ES 里的历史有效数据。后续若要
让企业查询页和其他任务立即共享刷新结果，再实现 staging + commit 的 ES 投影，不采用旧系统的
先删后写方式。

真实联调还需要在 Atlas 部署环境提供以下变量并确认服务器可访问接口：

```text
ATLAS_COMPANY_REFRESH_ENABLED=true
ATLAS_COMPANY_REFRESH_BASE_URL=https://openapi.xiaolanben.com/api/
ATLAS_COMPANY_REFRESH_ACCESS_ID=<受控密钥>
ATLAS_COMPANY_REFRESH_ACCESS_TOKEN=<受控密钥>
```

dispatcher 源码中现存的历史明文凭据没有复制到 Atlas，建议另行轮换。
