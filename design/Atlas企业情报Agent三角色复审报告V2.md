# Atlas 企业情报 Agent 三角色复审报告 V2.0

> 复审对象：`Atlas企业情报Agent详细设计V1.md`（V1.1）、`atlas-agent-full-platform.html`  
> 复审角色：产品、研发、企业风险运营  
> 复审日期：2026-07-29  
> 复审结论：**通过 V1 核心链路研发评审；仍不等于达到生产上线条件。**

## 0. 复审后业务确认补充

业务负责人已在复审后进一步确认：

- V1 只做单企业旧风险报告更新；
- 不区分普通运营和高级运营，暂时不设置审核人、二审或审批；
- 运营人员完成人工研判后可直接生成正式 DOCX；
- 原始分与人工分分别保存，所有调整保留原因和操作记录；
- 风险等级为高 `[8,10]`、中高 `[6,8)`、中 `[4,6)`、中低 `[2,4)`、低 `[0,2)`；
- 失联、欠薪最低原始分为 6.0，闭店最低原始分为 8.0；
- 开发使用 JSON/离线数据，生产通过只读适配器查询 ES；
- 只复用旧模型评分规则，评分与报告存储重新设计；
- 多个主流搜索引擎和多个大模型搜索服务联合检索；
- 必查查询失败时任务停止，修复后继续；
- 开发中间件由 Docker Compose 启动；
- 现有 DOCX 示例作为 V1 正式模板，PDF 后置。

因此，本报告后文关于“风险审核人、二审和批准正式报告”的建议不再作为 V1 要求；相关能力只保留为未来扩展。操作记录仍然保留，它属于可追溯性，不属于审批流程。

## 1. 执行结论

本轮调整解决了上一轮最关键的结构性问题：

1. 第一版的唯一业务目标已冻结为“单企业旧风险报告更新”；
2. 招商线索、批量调查和完整平台建设不再进入 V1 验收；
3. 普通运营导航从十多个平台页面收敛为五个业务入口；
4. 新增独立、高保真的待办复核工作台；
5. 稳定企业 ID、物理数据表、同步快照和存储职责已有明确设计；
6. 旧风险评分模型不再以完整 `updateRiskInfo` 直接在线调用；
7. 公开搜索接入、失败语义、证据字段和来源新鲜度已有正式方案；
8. 技术 SLO 与业务效果指标已分开定义。

综合判断从上一轮的“有条件通过立项评审”提升为：

> **可以启动 V1 核心生产链路研发，但启动的是风险报告更新链路，不是完整企业情报平台。**

当前仍有三项上线前硬门槛：

- 用真实数据验证企业身份绑定和旧 ID 迁移；
- 确定生产可用的公开搜索/内容服务及授权边界；
- 建立 20～50 组成对历史报告的黄金评测集并跑出基线。

## 3. 产品角色复审

### 3.1 产品结论

**通过。**

本轮最重要的提升不是新增了页面，而是产品价值主张终于稳定：

> 用户上传或选择一份旧风险报告，用自然语言提出核查要求，Agent 完成数据核验和差异发现，运营人员在同一工作台复核并形成新版报告。

这个闭环具备明确用户、明确输入、明确输出和可量化的效率价值，已经能够支撑产品立项和故事拆分。

### 3.2 改进有效的地方

#### 1. V1 不再同时承担两类业务

招商线索仍然是 Agent 将来可复用同一底座承载的能力，但不再干扰第一版的数据、规则、界面和验收设计。产品不需要同时解释“风险准确性”和“招商推荐价值”两套完全不同的目标。

#### 2. 对话入口与生产流程衔接

对话页不再只是演示回答：

- 可绑定旧报告；
- 展示企业主体和任务快照；
- 展示各数据源执行状态；
- 返回的是调查草稿；
- 明确进入“待办复核”，而不是直接生成正式结论。

这使对话成为任务入口，而不是整个产品本身。

#### 3. 成功指标更接近业务价值

新增端到端处理时间、人工有效操作时间、一次通过率、结论修改率、重大结论驳回率和新增有效风险发现率。它们能够判断产品究竟是减少了运营工作，还是只增加了一个生成步骤。

#### 4. 前台与后台分离

普通运营人员只看到 Agent、任务、复核、企业、报告五个入口。Skills、工具、数据源、规则、模型和评测进入管理后台，降低了认知负担，也更符合权限边界。

### 3.3 仍需产品确认

以下内容不阻塞核心研发，但需要在试运行前冻结：

1. 哪些任务默认要求二审；
2. 哪些风险类型允许运营人员自行改分；
3. 旧报告是否必须上传，还是也允许从报告中心选择；
4. 数据来源部分失败时，报告是允许以“部分完成”提交，还是必须阻塞；
5. 运营任务超时、转交和催办规则；
6. 正式报告模板的章节级差异如何展示和确认。

## 4. 研发角色复审

### 4.1 研发结论

**通过核心链路架构评审，可以进入接口契约、数据表和兼容层开发。**

V1.1 已从逻辑架构补到了可以拆研发任务的物理设计层。尤其是企业身份、任务快照、模型副作用和 ES 职责这四个问题，已经有足够明确的实现方向。

### 4.2 改进有效的地方

#### 1. 企业主键决策正确

内部不可变 UUID 与外部身份锚点分离，避免统一社会信用代码缺失、变更、注销、重复数据或历史来源差异导致主键不稳定。身份绑定表保留旧 MD5 和 ES ID，为现有资产迁移提供了路径。

研发时还应加入：

- 身份绑定变更审计；
- 企业合并与撤销合并；
- 低置信度人工确认；
- 历史报告在主体合并后的可追溯关系。

#### 2. 快照一致性能够支撑报告审计

同一任务冻结 `snapshot_id`，来源更新不悄悄改变正在审核的报告；用户主动刷新时创建新快照并产生差异。这一决定解决了“为什么同一份报告前后分数不一样”这一常见审计问题。

#### 3. 数据存储职责清楚

- PostgreSQL：任务、身份、发现、人工结论、评分快照、报告版本；
- ES：可重建的检索投影；
- 对象存储：原始网页、附件和报告文件。

这比让 ES 同时承担事实库、版本库和审计库更稳健，也不要求迁移全部旧 mapping。

#### 4. 旧模型隔离方案可行

文档不再假设加一层 Facade 就能消除副作用，而是把 `updateRiskInfo` 视为需要隔离的遗留编排：

- 先固化黄金样本；
- 再只读影子运行；
- 然后抽取纯计算；
- 最后新旧引擎并行对比。

这条路径既不丢弃旧资产，也不会把 Redis、通知、队列和写库副作用带进 Agent 工具调用。

#### 5. 外部来源失败语义正确

“查询成功但 0 条”和“查询失败”分开建模，外部来源不可用时标记部分完成，不允许评分系统解释成无风险。该规则应落实为统一错误码和任务状态，而不只是界面文案。

### 4.3 开发前必须完成的技术验证

#### A. 企业身份小样迁移

从 `company_data` 和两个 JSON 样本中抽取至少 100 家企业，验证信用代码、名称、旧 MD5、ES ID 和来源 ID 的绑定覆盖率，并保留冲突样本。

#### B. 旧评分影子执行

确认禁用以下副作用后能够稳定运行：

- 数据库更新；
- Redis 写入；
- 消息队列；
- 告警或通知；
- 随机等待；
- 隐式外部查询。

若无法通过开关完全禁用，应使用独立进程和只读依赖，不允许在主任务进程中直接调用。

#### C. 搜索接入选型

至少确定一个生产主渠道和一个人工兜底方案，并验证：

- 调用配额与成本；
- 可保存字段；
- 结果时效；
- 查询与正文使用授权；
- 限流和失败处理；
- 对中文企业名、品牌名和简称的检索质量。

#### D. 容量参数实测

“千万级主档、亿级事件”是设计基线，不是已验证事实。需要用旧 ES 实际文档数、日增量、文档平均大小、三年在线量和峰值并发替换估算，并完成至少一次压测。

## 5. 运营角色复审

### 5.1 运营结论

**通过运营走查前评审。**

上一轮原型最大的问题是只有“Agent 给出摘要”，没有“运营人员怎样完成一天的复核工作”。本轮新增的待办复核工作台已经能够表达真实动作。

### 5.2 复核工作台覆盖的关键动作

| 运营动作 | 本轮表现 |
|---|---|
| 选择待办 | 左侧队列展示企业、优先级、发现数量和等待时间 |
| 确认主体 | 主体信用代码、快照和官方来源在同屏展示 |
| 核对风险发现 | 风险类型、严重度、主体归属和限定语可单独处理 |
| 查看原始证据 | 右侧展示来源、时间、主体匹配、摘要和证据状态 |
| 核对数据新鲜度 | 工商、司法、内部 ES 和公开检索分别展示截止时间 |
| 处理门店归属 | 明确区分已确认 2 家和仅品牌关联 3 家 |
| 人工改分 | 同屏展示模型原始分 8.0、人工分 9.8、原因码和说明 |
| 对比报告 | 旧版与新版逐段显示删除、新增和评分变化 |
| 提交审核 | 支持补充调查、保存草稿和提交二审 |

这已经足以组织一次真实运营走查，并收集字段、顺序和权限反馈。

### 5.3 仍需运营验证

原型当前使用的是示例数据，以下问题必须由实际使用人员现场操作后确认：

1. 一屏三栏的信息密度是否适合 1366×768 的办公设备；
2. 运营人员更习惯按“风险发现”还是按“报告章节”复核；
3. 证据摘要是否足够，哪些风险必须查看全文或附件；
4. 改分原因码是否覆盖现有人工评分标准；
5. 门店关闭、失联、欠薪各自需要哪些专属字段；
6. 是否需要任务评论、@审核人、交接和催办；
7. 批量处理是否应进入下一阶段，而不是 V1 首发。

## 6. 原型复审

### 6.1 信息架构

普通运营导航已收敛为：

```text
Agent 对话
调查任务
待办复核
企业档案
报告中心
```

管理后台作为单独入口，再进入 Skills、工具、策略、数据源、规则、模板、模型、评测、监控、审计和权限。这个结构既保留完整平台设计，也没有让运营人员承担平台内部概念。

### 6.2 交互闭环

当前原型已经可演示：

```text
对话下达任务并绑定旧报告
→ 查看主体、快照和 Agent 执行过程
→ 进入待办复核
→ 切换风险结论 / 报告差异 / 评分调整
→ 查看证据和来源新鲜度
→ 保存、退回补充或提交二审
→ 在报告中心查看版本状态
```

### 6.3 视觉判断

业务已确认生产版本保留两套主题：

- “冰川运营”作为默认主题，适合运营人员长时间使用；
- “墨玉政企”作为可切换主题，适合正式展示和政企场景；
- 字号、间距和对比度使用统一设计令牌。

编辑部情报、深色科技和石墨指挥不进入 V1 主题选择器，避免持续维护五套主题。

## 8. 建议研发顺序

### 工作包 1：契约与企业身份

- 冻结 Company、Snapshot、Evidence、Finding、RiskScore、ReportVersion 契约；
- 建立核心表和身份绑定；
- 完成 100 家企业小样迁移验证。

### 工作包 2：数据快照与确定性工具

- 接入 `company_data` 和可用业务服务；
- 建立水位、同步批次、当前/历史和任务快照；
- 完成工商、标准风险、旧报告解析工具。

### 工作包 3：评分影子与评测集

- 建立 20～50 组成对历史报告；
- 隔离旧评分模型副作用；
- 保存模型原始分、人工分、原因和规则版本；
- 跑出基线，不先承诺主观准确率。

### 工作包 4：公开检索与证据

- 确定生产搜索渠道；
- 实现结果去重、主体匹配、内容指纹和失败语义；
- 打通证据原文或附件保存。

### 工作包 5：Agent 与复核工作台

- 实现对话创建任务、旧报告绑定和执行状态；
- 实现风险发现、证据核验、报告差异和人工改分；
- 完成权限、审计和二审门禁。

### 工作包 6：报告与端到端验收

- 根据正式 Word 模板生成草稿；
- 复核通过后生成正式版；
- 使用黄金评测集和真实运营人员完成端到端走查；
- 依据实测基线冻结试运行目标。

---

## 9. 暂不启动的内容

- 完整招商线索产品；
- 批量企业风险调查；
- 多 Agent 协作框架；
- 全量旧 ES mapping 迁移；
- 编辑部情报、深色科技和石墨指挥三套主题的生产级维护；
- 自动对外发布正式报告；
- 复杂企业图谱可视化；
- 面向普通运营的 Skills、工具和模型配置。

这些能力不是被放弃，而是在 V1 验证“报告更新效率和质量”之后再决定优先级。
